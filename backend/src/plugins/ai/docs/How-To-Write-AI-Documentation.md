# Как да пишете документация за AI асистента

Това ръководство обяснява как да създавате ефективна документация, която AI асистентът може да чете и използва за отговори на потребителски въпроси.

---

## Основни принципи

### 1. Ясна структура
AI чете документацията **линейно** (отгоре надолу). Организирайте информацията логично:
- **Общ преглед** → **Детайли** → **Примери** → **Troubleshooting**

### 2. Кратък и точен език
- Избягвайте дълги изречения.
- Използвайте **bullets** за списъци.
- Една идея = Един параграф.

### 3. Контекст преди детайли
Винаги обяснявайте **защо** преди **как**:
```markdown
❌ Лошо: "Натиснете бутона 'Generate'."
✅ Добро: "За да създадете firmware, натиснете 'Generate'."
```

## Структура на документа

### Препоръчителен шаблон

```markdown
# [Заглавие на функцията]

> [!IMPORTANT] AI INSTRUCTION (ако е нужно)
> Специални инструкции за AI (напр. "Представяй стъпка по стъпка").

## Overview (Общ преглед)
Кратко обяснение какво прави тази функция и защо е полезна.

## Accessing (Достъп)
Как потребителят достига до тази функция.

## Step-by-Step Process (Стъпка по стъпка)
### Step 1: [Име на стъпката]
- Какво се случва
- Какво трябва да направи потребителят
- Важни бележки

### Step 2: [Име на стъпката]
...

## Troubleshooting (Решаване на проблеми)
Чести грешки и как да се поправят.
```

## Използване на GitHub Alerts

AI разбира и обръща специално внимание на GitHub-style alerts. Използвайте ги стратегически:

### NOTE (Бележка)
За допълнителна информация, която не е критична:
```markdown
> [!NOTE]
> Това е полезна информация, но не е задължителна.
```

### TIP (Съвет)
За best practices и препоръки:
```markdown
> [!TIP]
> Препоръчваме да използвате Serial връзка за критични сензори.
```

### IMPORTANT (Важно)
За ключова информация, която потребителят трябва да знае:
```markdown
> [!IMPORTANT]
> Изберете правилния волтаж, иначе сензорът няма да работи.
```

### WARNING (Предупреждение)
За потенциални проблеми:
```markdown
> [!WARNING]
> Грешна WiFi парола ще изисква повторно генериране на firmware.
```

### CAUTION (Внимание)
За критични действия, които могат да причинят загуба на данни или повреда:
```markdown
> [!CAUTION]
> Избор на грешен board type може да повреди контролера.
```

## Специални AI инструкции

За туториали и стъпкови процеси, добавете инструкции за AI в началото:

```markdown
> [!IMPORTANT] AI INSTRUCTION
> When using this document to help a user, **DO NOT READ THE WHOLE FILE AT ONCE**.
> Ask the user: "Shall we start Step 1?".
> Present **Step 1 ONLY**. Wait for confirmation.
> Present **Step 2 ONLY**. Wait for confirmation.
> Repeat until finished.
```

Това кара AI да води потребителя **интерактивно**, вместо да изсипе цялата информация наведнъж.

## Форматиране на текста

### Заглавия
Използвайте йерархия:
```markdown
# Главно заглавие (H1) - Име на функцията
## Секция (H2) - Overview, Steps, Troubleshooting
### Подсекция (H3) - Step 1, Step 2
#### Детайл (H4) - Option A, Option B
```

### Удебеляване
- **Bold** за важни термини и действия: `**Firmware Builder**`
- *Italic* за примери и пояснения: `*Example: Arduino Uno R3*`
- `Code` за технически термини: `` `WiFi SSID` ``

### Списъци
**Bullets** за неподредени елементи:
```markdown
- Първо нещо
- Второ нещо
```

**Numbered lists** за стъпки:
```markdown
1. Отворете страницата
2. Натиснете бутона
3. Въведете данните
```

## Примери и конкретика

### ❌ Лошо (твърде абстрактно)
```markdown
Изберете подходящата опция за вашата конфигурация.
```

### ✅ Добро (конкретно)
```markdown
Изберете **Serial** ако контролерът е близо до сървъра, или **WiFi** ако е на разстояние.
```

### ✅ Още по-добро (с пример)
```markdown
Изберете **Serial** ако контролерът е близо до сървъра (до 5 метра), или **WiFi** ако е на разстояние.

**Пример:** За pH сензор в резервоар до компютъра → Serial. За сензор в оранжерия на 20 метра → WiFi.
```

## Troubleshooting секция

Винаги добавяйте секция за чести проблеми:

```markdown
## Troubleshooting

**[Проблем]:**
- [Причина 1] → [Решение]
- [Причина 2] → [Решение]

**Пример:**
**Controller not connecting after upload:**
- Verify WiFi credentials (SSID/Password) if using WiFi transport.
- Check that the controller and server are on the same network.
```

## Дължина на документа

- **Кратки документи** (до 100 реда) → Добре за прости функции.
- **Средни документи** (100-200 реда) → Идеални за туториали.
- **Дълги документи** (200+ реда) → Разделете на няколко файла.

**Правило:** Ако документът е над 300 реда, разделете го на:
- `Feature-Overview.md` (общ преглед)
- `Feature-Step-by-Step.md` (детайлен туториал)
- `Feature-Troubleshooting.md` (проблеми и решения)

---

## Многоезичност

Ако пишете на български:
- Използвайте **прости думи**.
- Избягвайте жаргон (освен ако не го обясните).
- Технически термини оставете на английски в `` `backticks` ``.

**Пример:**
```markdown
За да настроите **WiFi връзката**, въведете `WiFi SSID` (името на рутера).
```

---

## Тестване на документацията

След като напишете документ:

1. **Попитайте AI:** "Как да създам firmware?"
2. **Проверете дали AI:**
   - Дава точна информация
   - Следва стъпките правилно
   - Споменава важните предупреждения

3. **Ако AI греши:**
   - Добавете повече контекст
   - Удебелете ключовите думи
   - Добавете Alert блокове

## Checklist за качествена документация

- [ ] Има ясно заглавие (H1)
- [ ] Започва с Overview секция
- [ ] Стъпките са номерирани и логични
- [ ] Има примери за всяка важна стъпка
- [ ] Използва Alerts за важна информация
- [ ] Има Troubleshooting секция
- [ ] Дължината е под 300 реда (или е разделена)
- [ ] Тествана с AI асистента
